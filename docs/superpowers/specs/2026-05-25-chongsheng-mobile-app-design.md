# 宠生手机 App 高保真原型设计规格

日期：2026-05-25

## 1. 目标与定位

宠生是一款围绕宠物数字分身与陪伴互动的手机 App。长期愿景是让用户上传宠物照片和日常视频，提取宠物外形、行为、习惯与互动偏好，生成可由大模型驱动的 UE 虚拟 3D 宠物，并通过 MCP 能力节点向大模型暴露记忆、情绪、动作和回应能力。

第一版不做真实完整技术链路，而是做一套手机端高保真可点击原型。原型要让用户在 3 分钟内理解：宠生可以保存宠物习惯、构建数字分身，并让这个分身在房间里以动作、语音、文字和 UI 互动回应用户。

产品表达支持两类场景：

- 在世宠物的日常数字分身与互动陪伴。
- 已故宠物的纪念与再陪伴。

第一版文案必须克制，不承诺“复活”，不暗示真实意识或真实情感。推荐表达是“数字分身”“习惯记忆”“延续陪伴”“让 TA 更像自己”。

## 2. 第一版范围

第一版交付物是手机 App 高保真原型，不是 Web 端产品，也不是完整真机工程。浏览器只用于展示移动端 mockup 和流程图。

已确认范围：

- 平台形态：手机 App 高保真可点击原型。
- 主入口：宠物房间开场。
- 视觉气质：日常陪伴感为主，温柔、明亮、亲近。
- 互动入口：文字、语音、UI 场景按钮三者都出现，但以轻量模拟跑通闭环。
- 视频行为提取：半技术展示，包含视频帧、识别进度、置信度、行为时间线。
- UE 表现：强调虚拟宠物在房间内的动作控制，如走近、摇尾、趴下、靠近镜头。
- MCP 呈现：互动时轻量可视化调用链，如读取习惯、判断情绪、播放动作、生成回应。

第一版不做：

- 真实照片转 3D 模型生产管线。
- 真实 UE 云渲染或 UE Runtime 集成。
- 完整账号、支付、社区、分享体系。
- 开发者模式 MCP 后台、完整 tool schema UI 和调用日志后台。
- 长期记忆的真实云端同步。

## 3. 核心体验流程

主流程：

1. 用户打开 App，直接进入宠物房间。
2. 房间里展示 UE 风格的数字宠物预览，宠物会做轻量动作。
3. 用户看到“让 TA 更像自己”的引导。
4. 用户上传宠物照片，补充名字、称呼、物种、年龄和性格线索。
5. 用户上传日常视频，进入行为分析过程。
6. App 展示视频代表帧、行为识别进度、置信度和行为时间线。
7. 行为档案生成习惯标签和短摘要。
8. 用户回到宠物房间，通过文字、语音或场景按钮发起互动。
9. 界面展示轻量 MCP 调用链。
10. 数字宠物做出 UE 风格动作，并给出短回应。

体验原则：

- 先让用户觉得“TA 在这里”，再提示上传更多素材会让 TA 更像自己。
- 上传和建档是渐进任务，不是一次性大表单。
- 技术能力要被用户感知，但不能压过陪伴感。
- 纪念场景文案要温柔，不能操纵悲伤。

## 4. 核心页面

第一版建议控制在 7 个可点击页面以内。

### 4.1 宠物房间

默认首页。页面展示数字宠物、房间环境、今日状态、互动入口和“完善 TA”的任务提示。

关键元素：

- UE 风格宠物预览区域。
- 当前场景，如客厅、窗边、睡前。
- 今日情绪或状态，如“想玩球”“有点想靠近你”。
- 底部互动入口：语音、动作、习惯、记忆。
- 渐进任务入口：“让 TA 更像自己”。

### 4.2 首次创建

用户为宠物建立基础档案。流程要短，先收集最影响情感连接的信息。

字段：

- 名字。
- 物种。
- 常用称呼。
- 年龄或陪伴时间。
- 场景类型：日常陪伴或纪念陪伴。

### 4.3 照片上传

用于生成数字形象草稿。第一版只做模拟资产，不承诺真实照片生成 3D。

体验：

- 支持上传或选择样例照片。
- 展示“正在提取毛色、脸型、体态特征”的过程。
- 生成一个可信的 3D 宠物预览占位。

### 4.4 视频上传

用于提取行为特征。第一版以半技术展示增强可信度。

体验：

- 上传或选择样例日常视频。
- 展示抽帧过程。
- 展示识别中的行为片段。
- 输出行为标签和置信度。

### 4.5 行为档案

展示从视频与用户补充信息中形成的习惯记忆。

内容：

- 代表帧。
- 行为时间线。
- 置信度标签。
- 性格摘要。
- 可用于互动的习惯卡片。

样例标签：

- 听到名字会抬头。
- 睡前喜欢靠近人。
- 看到球会兴奋。
- 被轻声呼唤时会慢慢走近。

### 4.6 互动回应

用户通过文字、语音或 UI 场景按钮触发互动。

交互样例：

- 用户输入：“过来陪我一下。”
- UI 按钮：“叫 TA 过来”“一起玩球”“睡前陪伴”。
- 语音入口：展示录音波形和识别文本。

回应由短句与动作组合：

- 动作：走近、摇尾、趴下、靠近镜头。
- 短句：“我记得你睡前喜欢让我靠近一点。”

### 4.7 记忆详情

展示某个习惯或记忆片段如何影响回应。

内容：

- 记忆来源：视频识别、用户补充、历史互动。
- 最近一次触发。
- 与回应动作的关系。

## 6. MCP 能力节点草案

MCP 在首版用户界面中只显示调用链摘要，不暴露完整参数。规格文档保留未来 schema 方向，便于后续真实实现。

### 6.1 pet.memory.query

用途：查询与当前用户输入、场景和宠物状态相关的习惯或记忆。

输入草案：

- petId。
- query。
- context，如当前场景、时间、用户情绪线索。

输出草案：

- matchedMemories。
- relevance。
- suggestedTone。

### 6.2 pet.behavior.summarize

用途：将视频行为识别结果整理成可用于互动的习惯摘要。

输入草案：

- petId。
- mediaAssetIds。
- confidenceThreshold。

输出草案：

- behaviorInsights。
- habitSummary。
- uncertainFindings。

### 6.3 pet.emotion.infer

用途：结合用户输入、宠物档案和上下文推断互动情绪。

输入草案：

- userInput。
- interactionMode。
- petProfile。
- recentMemories。

输出草案：

- emotion。
- intent。
- responseStyle。

### 6.4 pet.motion.play

用途：驱动 UE 或模拟层播放宠物动作。

输入草案：

- petId。
- motionName。
- intensity。
- cameraHint。

输出草案：

- status。
- animationClip。
- durationMs。

### 6.5 pet.response.compose

用途：生成短回应，和动作保持一致。

输入草案：

- userInput。
- petMemories。
- inferredEmotion。
- motionResult。

输出草案：

- responseText。
- voiceHint。
- nextSuggestedActions。

## 7. 技术架构边界

首版原型分为六层概念边界：

- 移动端体验层：手机 App 页面、点击路径、上传模拟、MCP 调用链展示。
- 宠物档案服务：宠物基础信息、素材、习惯、记忆和互动历史。
- 行为理解服务：抽帧、行为识别、时间线、置信度和性格摘要。
- MCP 能力层：对大模型暴露记忆、行为、情绪、动作和回应能力。
- UE 动作运行时：宠物 Actor、动作状态机、房间场景、镜头和姿态控制。
- 大模型编排层：根据用户输入与宠物习惯决定调用哪些能力节点。

首版实现时，这些层都可以被模拟数据驱动，但代码结构和原型叙事要保持可替换边界。

## 8. 关键架构决策

### ADR-001：首版做手机 App 高保真原型，而不做 Web 产品

状态：Accepted

背景：用户明确希望做手机 App 端，不想做 Web 端。第一版需要验证产品体验和叙事，而不是验证 Web 技术栈。

决策：第一版交付手机 App 高保真可点击原型。浏览器只作为预览和演示载体。

影响：

- 正向：更贴近真实使用场景，更容易验证陪伴感。
- 负向：若后续要做真机工程，需要再选择 iOS、Android 或跨平台技术栈。
- 中性：原型工具和真实 App 工程可以分离。

### ADR-002：首版模拟 AI、UE 和 MCP 全链路

状态：Accepted

背景：真实照片转 3D、视频理解、UE 动作运行时和 MCP 编排都存在较高工程复杂度。若首版全部真实实现，会推迟用户体验验证。

决策：首版使用固定样例、状态机和本地模拟数据实现完整体验闭环。文档中明确每个模拟点未来对应的真实服务。

影响：

- 正向：Demo 稳定，能快速验证用户是否理解并喜欢这个方向。
- 负向：技术可行性仍需要后续专项验证。
- 中性：原型必须在 UI 中避免暗示所有能力已真实落地。

### ADR-003：MCP 对用户轻量可视化，不做开发者后台

状态：Accepted

背景：MCP 是产品技术壁垒，但首版用户不是开发者。完整 schema 和调用日志会干扰陪伴体验。

决策：互动时展示简化调用链，如“读取习惯记忆 → 判断情绪 → 播放动作 → 生成回应”。完整 MCP 节点只写入设计文档。

影响：

- 正向：用户能理解回应不是随机的，同时保持界面温暖。
- 负向：技术受众可能需要额外说明材料。
- 中性：未来可以增加开发者或合作方模式。

## 9. 非功能要求

### 9.1 原型性能

- 页面切换应感觉即时，目标是 300ms 内完成可见反馈。
- 模拟分析过程可以有 2 到 5 秒进度动画，用于表达任务存在。
- 动作回应应在用户触发后 1 秒内开始出现。

### 9.2 可用性

- 用户 3 分钟内应理解核心价值。
- 用户不需要读说明文案，也能完成一次“上传素材 → 行为档案 → 互动回应”闭环。
- UI 文案不使用复杂技术词作为主标题。

### 9.3 隐私与安全

- 原型文案应提示照片和视频属于敏感私人素材。
- 后续真实产品必须支持删除宠物档案、删除素材和导出数据。
- 纪念场景不得使用诱导性付费或情绪勒索文案。

### 9.4 可维护性

- 模拟数据应集中管理。
- 交互状态与页面表现分离。
- 未来接入真实服务时，应能替换上传、分析、MCP 调用和 UE 动作四类适配器。

## 10. 错误与空状态

原型需要覆盖以下状态：

- 未上传素材：宠物房间仍可体验样例互动，但提示“上传后会更像 TA”。
- 视频分析中：显示抽帧、识别中、生成习惯三个阶段。
- 分析置信度低：展示“还需要更多日常视频来确认”。
- 互动输入为空：提示用户说一句话或选择场景按钮。
- 动作不可用：降级为短回应和轻量表情动画。

## 11. 测试与验证

### 11.1 原型走查

必须完成以下路径：

- 首次打开 App 进入宠物房间。
- 创建宠物档案。
- 上传照片并生成形象草稿。
- 上传视频并看到行为分析过程。
- 查看行为档案。
- 发起文字互动。
- 发起语音模拟互动。
- 使用 UI 场景按钮触发动作回应。
- 查看 MCP 调用链。
- 查看记忆详情。

### 11.2 体验验证问题

用户测试时关注：

- 用户是否能在 3 分钟内说出宠生是做什么的。
- 用户是否觉得宠物房间比建档向导更有吸引力。
- 用户是否理解行为分析结果来自视频。
- 用户是否理解 MCP 调用链表达的是“系统如何做出回应”。
- 用户是否觉得纪念场景文案温柔但不过度。

### 11.3 残余技术风险

- 真实照片到 UE 3D 模型的质量、成本和时延。
- 视频行为识别对不同物种、品种和拍摄质量的鲁棒性。
- 大模型生成回应时的幻觉和情感边界。
- UE 动作运行时在手机端或云端的性能与成本。
- MCP 能力节点的权限、审计和隐私控制。

## 12. 后续实施建议

下一步应进入实现计划阶段。建议实施顺序：

1. 搭建手机 App 原型工程或原型页面结构。
2. 建立模拟数据和状态机。
3. 实现宠物房间首页。
4. 实现创建、照片上传和视频上传流程。
5. 实现行为档案和分析时间线。
6. 实现互动面板、MCP 调用链和 UE 动作模拟。
7. 做移动端视觉打磨和完整走查。
